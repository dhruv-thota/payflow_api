# PayFlow API

A simplified UPI-style payment backend built using **Java 17, Spring Boot, Spring Data JPA, and H2 Database**.

The project demonstrates how to build a layered REST API using Spring Boot, including entity mapping, repository queries, dependency injection, REST controllers, JSON request handling, and an embedded database.

---

## 1. Tech Stack

- **Java:** 17
- **Spring Boot:** 3.3.4
- **Build Tool:** Maven
- **Web Framework:** Spring Web / Spring MVC
- **Persistence:** Spring Data JPA / Hibernate
- **Database:** H2 in-memory database
- **Testing:** Spring Boot Starter Test
- **API Style:** REST
- **JSON:** Jackson

## 3. Architecture

The application follows a layered architecture:

```text
HTTP Request
     │
     ▼
Controller Layer
     │
     ▼
Service Layer
     │
     ▼
Repository Layer
     │
     ▼
H2 Database
```

### Controller Layer

Handles HTTP requests and responses.

- `UserController`
- `TransactionController`

### Service Layer

Contains the application/business operations and delegates persistence operations to repositories.

- `UserService`
- `TransactionService`

### Repository Layer

Uses Spring Data JPA to communicate with the database.

- `UserRepository`
- `TransactionRepository`

### Entity Layer

Defines the database-mapped domain objects.

- `User`
- `Transaction`

## 5. Entities

### User

The `User` entity represents a PayFlow user.

Fields:

| Field | Type | Database Column |
|---|---|---|
| `id` | Long | `id` |
| `name` | String | `name` |
| `upiId` | String | `upi_id` |
| `phoneNumber` | String | `phone_number` |
| `balance` | Double | `balance` |

The primary key is generated using:

```java
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

### Transaction

The `Transaction` entity represents a money transfer.

Fields:

| Field | Type | Database Column |
|---|---|---|
| `id` | Long | `id` |
| `senderUpiId` | String | `sender_upi_id` |
| `receiverUpiId` | String | `receiver_upi_id` |
| `amount` | Double | `amount` |

The transaction stores sender and receiver UPI IDs as strings. There are intentionally no JPA relationships or foreign keys between `Transaction` and `User`.

---

## 6. Hibernate-Generated Tables

Hibernate automatically creates the database tables from the entity definitions.

The generated DDL is equivalent to:

```sql
create table "user" (
    id bigint generated by default as identity,
    balance float(53),
    name varchar(255),
    phone_number varchar(255),
    upi_id varchar(255),
    primary key (id)
);

create table transaction (
    id bigint generated by default as identity,
    amount float(53),
    receiver_upi_id varchar(255),
    sender_upi_id varchar(255),
    primary key (id)
);
```

H2 treats `USER` as a reserved keyword. Therefore:

```properties
spring.jpa.properties.hibernate.auto_quote_keyword=true
```

is enabled so Hibernate can safely create and access the `"user"` table.

## 7. Repository Layer

### UserRepository

`UserRepository` extends:

```java
JpaRepository<User, Long>
```

This provides standard operations such as:

- `save()`
- `findById()`
- `findAll()`
- `deleteById()`

It also contains a derived query:

```java
Optional<User> findByUpiId(String upiId);
```

Spring Data JPA derives the query from the method name.

For example:

```text
findByUpiId
```

is interpreted as:

```text
Find User where upiId equals the supplied value
```

Hibernate generated SQL similar to:

```sql
select
    u1_0.id,
    u1_0.balance,
    u1_0.name,
    u1_0.phone_number,
    u1_0.upi_id
from
    "user" u1_0
where
    u1_0.upi_id=?
```

The `?` is a parameter placeholder. The actual UPI ID is bound separately rather than being concatenated into the SQL string.

### Custom JPQL Query

The repository also contains:

```java
@Query("SELECT u FROM User u WHERE u.balance > :amount")
List<User> findUsersWithBalanceGreaterThan(@Param("amount") Double amount);
```

This uses JPQL, which operates on the entity and its Java properties rather than directly on database table names.

---

## 8. Query Approaches

Three common approaches are:

### 1. Derived Query

```java
Optional<User> findByUpiId(String upiId);
```

Spring Data derives the query automatically from the method name.

**Advantages:**

- Very little code
- Easy to read
- Good for simple queries

### 2. JPQL

```java
@Query("SELECT u FROM User u WHERE u.balance > :amount")
```

Useful when the query is more complex than what can conveniently be expressed through a method name.

### 3. Native SQL

A repository can execute database-specific SQL directly.

Native SQL provides maximum control over the SQL, but it is generally less portable and more tightly coupled to the database schema.

For this project, derived queries and JPQL are preferred because they provide sufficient functionality without unnecessary database-specific coupling.

## 13. `@RequestBody` and JSON Deserialization

The POST `/users` endpoint uses:

```java
@RequestBody User user
```

`@RequestBody` tells Spring MVC to read the HTTP request body and use an HTTP message converter to deserialize the JSON into a Java `User` object.

For example:

```json
{
  "name": "Priya",
  "upiId": "priya@okaxis",
  "phoneNumber": "9876543210",
  "balance": 1000.0
}
```

is converted into a `User` object.

Without `@RequestBody`, Spring MVC treats an unannotated complex parameter as a model attribute and attempts parameter-based binding rather than JSON body deserialization. Therefore, sending the JSON request body does not populate the Java object's fields in the same way.

The final implementation restores `@RequestBody` because JSON request bodies are the intended input for these REST endpoints.

## 14. JSON Naming

The Java property is:

```java
private String upiId;
```

The database column is:

```text
upi_id
```

These are separate naming conventions.

The Java field is used by Jackson when mapping the JSON request/response, while JPA maps the Java property to the database column `upi_id`.

The API therefore uses:

```json
{
  "upiId": "priya@okaxis"
}
```

while the database uses:

```text
upi_id
```

## 15. Spring Dependency Injection

The services use Spring's dependency injection mechanism.

For example:

```java
@Service
public class UserService {

    @Autowired
    private UserRepository userRepository;
}
```

`@Service` tells Spring that `UserService` is a service-layer component managed by the Spring container.

Spring Data JPA creates the repository implementation automatically, and Spring injects that repository into `UserService`.

This avoids manually creating repository objects using `new`.

## 18. REST Request Lifecycle

A request such as:

```text
POST /users
```

passes through the Spring MVC infrastructure.

The request first reaches the embedded server and then the `DispatcherServlet`.

The `DispatcherServlet` uses Spring MVC's handler mapping infrastructure to identify the controller method responsible for the request.

A `HandlerAdapter` invokes the selected controller method and handles argument resolution, including `@RequestBody` JSON deserialization.

The controller delegates to the service, which delegates to the repository, and the repository persists the entity using JPA/Hibernate.

The resulting Java object is serialized back into JSON and returned as the HTTP response.

---

## 19. Stateless REST

The PayFlow API follows the stateless REST principle: each request contains the information necessary for the server to process that request.

The server does not depend on an in-memory session containing previous request state.

This makes it possible to run multiple instances of the API behind a load balancer.

For example:

```text
                  ┌──► PayFlow Instance 1
Client ──► Load ──┼──► PayFlow Instance 2
          Balancer └──► PayFlow Instance 3
```

Because requests are independent, a subsequent request does not have to reach the same application instance.

In this project, the H2 in-memory database is not intended for such a distributed production setup; a shared persistent database would be required for multiple application instances to share the same data.

---

## 20. H2 Persistence Behavior

The project uses an H2 **in-memory** database.

The database exists while the application process is running.

When the application is stopped, the in-memory database contents are lost.

Therefore, users and transactions inserted during one application run will not be available after restarting the application.

This differs from storing data in a Java `List`, although both approaches are in-memory from a persistence perspective. H2 provides an actual relational database engine with SQL, tables, transactions, and JPA integration, while a Java `List` is only an application-memory data structure.
